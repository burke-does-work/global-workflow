# Work Log

## 2026-09-06 -- Question rules split by function; person convention fixed

Asked for a review of `AGENTS.md` against `/style-guide`, plus internal consistency, conciseness, and repetition, with clarification requested on anything that would change agent behavior. Formatting came back nearly clean -- ASCII dashes and arrows, sentence-case headings, section rules, and trailing newline were all already right, which is the 2026-09-06 style sweep holding. Everything of consequence was behavioral.

The central finding is that "do not ask questions unless prompted" sorts by grammatical form rather than function. It reads as a blanket anti-question rule, and the file then requires asking in three separate places -- explaining before requesting approval, waiting for plan confirmation, and requesting completion sign-off. A rule that must be violated to comply elsewhere gets treated as soft, which is when the behavior it was meant to stop leaks back in. That is the mechanism worth remembering: the collision was not cosmetic, it was actively degrading the guardrail.

The first proposed fix declared "unless prompted" vestigial and cut it. That was wrong, and finding out why took the conversation somewhere better. The clause was doing real work -- it is the override hatch for the case where I tell a planning session to ask clarifying questions rather than make design assumptions on my behalf. So the line was two unrelated rules compressed into one: a ban on trailing questions that hand back the conversational lead, and a ban on clarifying questions with an escape hatch. Split them and both survive intact.

What I actually object to is narrower than "questions." It is a response ending in "what did you think about that?" or "is that how you felt?" I set the direction of a discussion and do not need prompting for it. Stated that way the rule stops colliding with approval gates, which are structural handoffs at defined points rather than solicitations of reaction.

The more useful discovery was that the interactive question widget is the friction, not questions as such. The evidence was in the session: two of those prompts were pushed at me and I rejected both, and the answers I gave in prose went places none of the preset options covered -- including the fact that "unless prompted" was an override, and that the popup itself was the problem. The widget forces the option space to be guessed in advance, which fails hardest during design clarification, where not knowing the option space is the whole reason for asking. Prose questions have no such failure mode: the answer is free to reframe the question. Written as a flat prohibition rather than a preference, deliberately, because some harnesses inject their own guidance pushing the other way.

That also settled a question left open earlier. With prose delivery the cost of a clarifying question is close to nothing -- no modal to dismiss, and it sits at the end of a response already being read -- so clarifying questions are now expected during the Plan stage rather than something I request each time. This inverts which case needs an instruction: suppression is now the exception.

Separately, `AGENTS.md` turned out to carry a person convention it never stated. `you` and `your` appeared on exactly two lines out of 186 and `I` never appeared; everywhere else the file uses bare imperative for instructions and names "the human" when the other party acts. The two exceptions were both in the work log section, and one of them inverted a rule: "when you signal completion" has two actors in scope and an undefined pronoun, so it reads as the agent's own completion signal when both clauses were meant to be mine. Wrote the convention into the header comment so the next edit does not break it again, rather than patching the two lines and leaving the rule implicit. Banned first person as well -- the file is configuration handed to whatever model loads it, so first person implies a speaker who is not there.

The stage vocabulary was stated three ways: the modes table said "plan, human review, build, test," the paragraph below said "spec, plan, implement," and the headings said something else again. Headings win, and spec came out of the table entirely because it is opt-in rather than part of the default complex flow. Dropped "human review" from the table cell as well, since review and approval requirements are stated properly elsewhere and duplicating them in a table cell is what let the three vocabularies drift apart in the first place.

Structural changes followed from the de-duplication. Design records and the work log both specified appending to the top, the same date-title format, and applying `/style-guide`; that boilerplate now sits once above both, in a new `## Reference documents` section. They had been filed under `## Completion`, which was wrong for the work log -- one of its two triggers is commit-message drafting, which is not completion. The commit rules were a single two-hundred-word paragraph carrying four separate rules and are now a short lead plus bullets, with no rule content altered; the "silence is inheritance" sentence from the previous session stands as written.

The skills list was trimmed to name plus trigger. Keeping it at all is a bet against drift -- eight descriptions maintained here that also live in each skill's frontmatter -- but the header comment claims tool-agnosticism and an agent without an auto-injected skill list gets nothing otherwise. Dropped the "compendium" reference rather than defining it; the term was explained nowhere in this file and only appears in `walkplan/SKILL.md`.

One process note worth recording, since it is evidence for the rules just written. The agent twice surfaced clarifying questions and then moved past them in the same response before I had answered, once closing with a plan proposal while four questions were still open. I had answered exactly one. That is the same failure the new rules address from the other side: questions delivered as decoration rather than as a genuine stop, which is what makes an agent's questions worth ignoring.

## 2026-09-06 -- Commit style layers instead of replacing

Found while an agent was checking its own commit messages against the template. Two of six wrapped a bullet across lines, and the report came back naming the wrap as the violation. The wrap was not the problem. Both bullets joined two claims with a semicolon, and wrapping was how that got hidden -- the report had diagnosed the symptom and called it the disease.

The template is why. `gitmessage` said "split a long line into another line -- do not wrap," which frames a semantic rule in typographic units. Following it literally, splitting is the only available remedy for a long bullet, and splitting a rambling bullet just produces two rambling bullets. `denning_and_outdoorsing_build/README.md` had the clause that fixes this -- "tighten wording before splitting a long bullet" -- and the template never got it. Same rule, two homes, one improved.

That is the drift, and it was structural rather than careless. `AGENTS.md` said a README `## Commits` section takes precedence "otherwise" the template, which makes an override total: the README must restate every rule it wants, including ones identical to the template. Under total replacement there is no shared rule, only a rule that happens to appear twice.

Chose to layer instead. The template is the base, a README section adds to or replaces individual rules, and anything unmentioned is inherited. The sentence carrying the weight is that silence is inheritance and never exemption -- merge models fail when absence is ambiguous between "inherit this" and "this does not apply." Overrides are stated as replacements rather than bare negations, because negating the `Type:` prefix leaves nothing behind describing what a subject should look like.

The alternative was keeping total replacement and fixing the wording in both files. It preserves insulation: a repo that rejects the shared convention does not silently inherit later changes to it. Rejected because the duplication is what drifted, and nothing structural stops it drifting again. The cost accepted is the mirror image -- template edits now reach every repo that has not overridden the rule being changed. Drift fails silently and at a distance; blast radius is visible at the moment of editing.

Denning's section dropped from eight bullets to five. Three were additions, four were restatements now inherited, and one was a genuine conflict restated positively as "subject: short summary, no type prefix." Two of the four restatements had been promoted out of that README and into the template on 2026-08-30, recorded in `dotfiles/WORK_LOG.md` for that date, so they had been redundant for a week.

Cleared `DESIGN_RECORDS.md` in this repo and in `dotfiles` in the same pass. Both had been seeded by sweeping their work logs, and on reading them back the entries were test material rather than decisions worth holding. The file stays in place, empty, for entries added deliberately. The work logs remain the narrative record and were not touched.

## 2026-09-06 -- DEV_HISTORY replaced by DESIGN_RECORDS

Went looking for an incomplete rename around a log file remembered as `dEV_LOG.md`. No such file ever existed. The name was a blend of two real ones: `DEV_HISTORY.md`, documented in `AGENTS.md` since 2026-06-29, and `WORK_LOG.md`, established across five repos on 2026-08-15. Seven `WORK_LOG.md` files exist on disk; `DEV_HISTORY.md` has never once been created.

Git dated the divergence precisely. The artifact lifecycle section describing `DEV_HISTORY.md` was written on 2026-06-29 and never touched again. On 2026-08-30 a commit went into the same file to make Work Log entries unconditional and left the `DEV_HISTORY` block eleven lines above it untouched. That is where the two parted: the work log gained two observable triggers, and the design record kept "on completion of a complex task."

So this was never a rename and never a disagreement. `DEV_HISTORY` was the June design, `WORK_LOG` the August design, and the September repos were applying August. `shop-system/WORK_LOG.md` records the supersession outright -- an earlier spec went to the bottom of that log "rather than into a `DEV_HISTORY.md`, since the work log supersedes that file" -- and `denning_and_outdoorsing_build/README.md` line 36 declares local rules govern because neither file exists there. Both were downstream of a stale paragraph nobody had removed.

The root cause is trigger design, not the idea. "Complex" and "important" are adjudicated downward in the moment; "you said done" and "a commit is being drafted" are not. This is also the documented way ADRs die in the field, so the failure was not specific to the setup.

Checked the concept against industry practice before rewriting it. Architecture Decision Records are the mainstream answer -- one file per decision, numbered, immutable, superseded rather than edited -- which means the instinct in the old line 137 was the standard one: reference docs describe what is, decision records describe why, and mixing them degrades both. What did not survive the check was the ceremony. Numbering, status workflow, and review gates buy team coordination, which is not a cost worth paying solo. RFC-style process gates were rejected outright as the wrong shape entirely.

Settled on `DESIGN_RECORDS.md`: one flat file per repo, ADR in spirit, formatted like `WORK_LOG.md` because that is the shape with demonstrated adherence here. Entries are immutable; a reversal is a new entry naming what it supersedes. The name avoids "log" deliberately, since that framing is what invited the old file to drift toward a changelog -- something line 137 had to explicitly deny.

Admission comes from a two-part test rather than a judgment of significance. A real alternative must have been considered and rejected, because if nothing was rejected it was not a decision, and reversing it now must cost more than an edit. The second half was added specifically because design decisions here are fluid; the rejected-alternative test alone would have admitted churn that resolves itself within a session.

Two triggers, with priority stated. The primary fires while writing a `WORK_LOG.md` entry, since most decisions are made mid-flight rather than at a milestone, and the design record is proposed in the same response so the proposal does not drift from the moment the reasoning is fresh. SPEC retirement is the secondary sweep. Naming retirement as the only trigger would have caught none of the five decisions already sitting in `shop-system`.

The two files differ on approval. Work log entries stay unconditional. Design records are proposed and written only on confirmation, on the grounds that a durable decision record deserves a look before it lands while a session log does not.

Retiring a `SPEC.md` is now explicitly the human's call. Line 96 already reserves SPEC alterations to the human, but "alters" does not obviously cover "disposes," and the lifecycle bullet sits in a section otherwise written as agent instructions. The costs are asymmetric -- an agent folding and disposing a spec unprompted destroys a human-owned document, while the guard costs one sentence. The spec now folds into two places rather than being archived whole: current-state content to `README.md`, or to whatever reference document serves that role where README is at capacity, and design decisions to `DESIGN_RECORDS.md`. The file is then disposed, since git retains it and both halves have homes.

Three alternatives were rejected along the way. Folding decision conclusions into a `README.md` section was the first recommendation and was dropped once the ADR comparison showed it cutting against the standard split; it also contradicted the original line 137. Per-module `DECISIONS.md` files were rejected in favour of one file per repo, since fewer places to check is worth more than tidier scoping at this volume -- entries carry a module prefix so a future repo split stays a grep-and-move. Forward pointers on superseded entries were rejected as unnecessary at the current iteration rate; that choice is load-bearing with newest-first ordering, which puts a superseding entry above the one it replaces, and would need revisiting if the order ever flipped.

`AGENTS.md` was aligned with `/style-guide` in the same pass: em dashes and arrows to ASCII, `## Working Relationship` and `### Work Log` to sentence case, and a missing trailing newline. Four pre-existing issues were cleared with it -- a bold-as-heading orphan at the old line 92 duplicating the `#### Spec` heading below it, a dangling "Phase 2" reference with no Phase 1 anywhere in the file, and "Claude" in a document whose own header claims tool-agnosticism. Adding an H1 was considered and skipped: the guide phrases that rule against a front-matter title, and this file has no front matter.

One consequence worth noting is that the `## yyyy-mm-dd -- Title` format in `AGENTS.md` had specified an em dash while every actual `WORK_LOG.md` already used `--`. The style sweep closed a mismatch between the instruction and seven files following it.

`DESIGN_RECORDS.md` was then seeded in three repos by sweeping their work logs: eleven entries in `shop-system`, nine here, seven in `dotfiles`. The `shop-system` file was seeded twice -- the first pass read only the opening forty-five lines of a hundred-and-seventy-line log and produced five entries, missing a second dated entry whose `Design decisions` and `Design history` sections were already written in exactly this shape.

Applying the admission test to these repos exposed a limit worth recording. "Reversing it now would cost more than an edit" screens well in a code repo, but `global_workflows` and `dotfiles` are repos whose product is text, so a literal reading excludes everything they contain -- reversing the unconditional work log rule is, literally, an edit. Read it instead as costing more than editing that text alone: the decision has downstream consequences, other files change, or behavior shifts across repos. Under the strict reading the work log rule would not qualify, which is plainly wrong, since it changed agent behavior in seven repos. The test needs that gloss written into `AGENTS.md` or it will be misapplied in every docs repo.

Cross-repo citation came up immediately. Three entries here -- the work log living in `AGENTS.md` rather than a skill, completion being signaled and never asked, and the `AGENT_LOG` to `WORK_LOG` rename -- were decided in a `dotfiles` session on 2026-08-15 but concern an artifact that lives here. Filed them where the artifact lives, since that is where someone asking why the rule is shaped this way will look, and pointed the citation at `dotfiles/WORK_LOG.md` for the narrative. The reciprocal case appears in `dotfiles`, where the unpromoted commit rules entry points here for the lookup order that resolves them.

`shop-system/WORK_LOG.md` was aligned to `/style-guide` in the same pass: twenty-three em dashes converted, all in the 2026-07-13 materials entry. Left alone deliberately were that entry's bold lead-ins, which the guide could be read to forbid as emphasis standing in for a heading. Converting them means rewriting the prose of a historical log entry rather than fixing its typography, and the append-only principle just established for design records argues the same way for work logs. Flagged rather than swept.

The admission test was then rewritten four times and finally abandoned, which was the right outcome and took too long to reach. The versions were: reversal costs more than an edit; something was given up to make the choice; it constrains what comes after; and it determines how something is rather than what was done. The first collapsed in `global_workflows` and `dotfiles`, where the product is text and reversing anything is an edit -- caught by actually running it against those repos rather than by reasoning about it. The second and third were significance filters wearing different clothes. The fourth was sound as a category description but useless as a gate.

The real problem was that I kept trying to make a judgment call checkable. Significance is not a property recoverable from the artifact; it is a call about the direction of the work, and it belongs to the human. Design decisions are now defined rather than tested -- significant calls made on the direction of the work -- with additions requested by the human. The agent does not ask whether something belongs, except when a `SPEC.md` is retiring, where the decisions are already written and the milestone is observable. That was always the only programmatic trigger; the work-log-time trigger was invention.

Also removed both sentences in the design records section that characterized `WORK_LOG.md`. One of them had described it as a record of actions, which is wrong -- the work log is a summary of thinking and conversation as much as of what was done, and that color is the point of keeping it. The wider lesson is that a section describing a neighbouring system it does not own will drift that system by degrees. The design records section now mentions the work log only to cite a date.

Dropped a twelfth `shop-system` entry proposed earlier for the stale OnShape cache. It was admitted by a test that no longer exists, and under the new rule that call is not the agent's to make.

## 2026-08-30 -- Commit style pointer added; md-guide replaced by style-guide

`AGENTS.md` told the agent to "match the commit style of the project" without saying where that style is defined. Working in `dotfiles`, Claude had nowhere to look, sampled `git log`, and picked up a type prefix that had been used once years into the history and was never valid. The instruction was sound; it just had no destination.

Fixed by stating a lookup order rather than a single source: a `## Commits` section in the repo `README.md` takes precedence where one exists, otherwise the repo's git commit template. Added an explicit prohibition on inferring style from `git log`, since history carries strays.

The precedence exists because `denning_and_outdoorsing_build` deliberately uses no type prefixes -- a docs-as-code convention worth keeping and likely to be reused in future docs repos. A bare pointer to the commit template would have sent agents to exactly the wrong vocabulary there.

Two alternatives were considered and rejected. Giving each docs repo its own commit template is conceptually tidier and would need no precedence logic, but `commit.template` lives in `.git/config`, which is neither tracked nor synced; on any machine where the pointer had not been set, an agent would silently read the global template and use the wrong vocabulary with no signal that anything was wrong. It would also reintroduce duplication inside a single repo. Naming the build repo as an exception directly in `AGENTS.md` was rejected as putting per-repo detail into a general working-relationship document, where it would accumulate into a list. The chosen approach adds no files and needs no per-machine setup. The build repo is currently the only repo with a `## Commits` section, so the discriminator is unambiguous, and any future docs repo overrides the same way.

Two Claude memory files duplicating that README section were deleted in the same pass, leaving the README as the single source. The README was already the more complete of the two, carrying a rule the memories did not record.

The Work Log rule itself was rewritten in the same session, after Claude missed it three times in a row. The cause was a genuine conflict: the rule said to *ask* whether to write an entry, while the newer interaction rule at the top of the file says not to ask questions unless prompted. Under that tension the ask kept losing, particularly mid-execution.

Resolved by making the entry unconditional -- write it, do not ask -- with two additions. The entry is written before the commit message is drafted, so it lands in the same commit as the work it describes rather than trailing it by one, which is what happened throughout this session. And writing it must be flagged in the response, so an unwanted entry is visible and can be removed; entries are appended to the top of the file, so undoing one is trivial. That trade was chosen over keeping the prompt and carving out an exemption in the interaction rules, on the grounds that an entry has been wanted every time so far and the unconditional version removes a decision point instead of adding a caveat.
